## 3. Defects found

### Fixed in this pass (branch `fix/live-e2e-final-2026-09-08`, commit `60fa4b6`)

**D1 — Every unambiguous bank match was reported as "No document". (High)**
`assessTransaction` returns `'confident'` for a lone clear winner. Four places in
`BankView.tsx` asked `kind === 'confused'`, so `'confident'` fell through to the red **"No
document"** pill, was counted in "£10,144.47 without evidence", was hidden from the "Needs
you" filter, and lost its Match button. The verdict's comment says a clear winner "is
linked without asking" — true only of the synthetic cast, because `autoMatches` is called
**only** from `buildInitialPipeline` and never on the API path; the server left all 17 rows
`UNMATCHED` and the `matches` table held 0 rows.

Live consequence: Currys £899.99/08 Aug, Wolseley £430.10/05 Aug and Wolseley £86.40 —
exact amount **and** date pairs — were each shown as having no document while their
invoices sat in the same inbox. The client was then chased for a receipt the product was
already holding, and the document's own detail said *"no imported transaction lines up with
this document"*, which was false.
*Fix:* one exported predicate `offersCandidates` used in all four places, so a fifth screen
cannot ask differently. Evidence `51`, `52`.

**D2 — A date nobody had read printed as today. (Medium)**
`api/documents.ts` maps `date: documentDate ?? receivedAt`, so a document still extracting
showed **08 Sep 2026** in the DATE column beside dates read off paper. Identical to the
£0.00 defect (#277) one column over.
*Fix:* `dateKnown` at the single mapping point and one `DocumentDate` cell on all seven
boards; the `receivedAt` fallback stays because sorting needs it. Evidence `46`.

### Found, diagnosed, located — not fixed

**D3 — The category enum faces the user on four surfaces. (Medium)**
The Ready board, the document detail, the bank match-candidate list and the Approvals card
render `FA_PLANT_AND_EQUIPMENT`, `REPAIRS_AND_MAINTENANCE`, `CLEANING_AND_WASTE`. The
publish review and the exported CSV render *"Fixed assets: Plant and equipment"* — so the
label exists and is correct server-side. This is the same defect the last walk fixed on the
approval card, still live on four others.
**Why I did not fix it:** `DocumentSummary` in `packages/contracts/openapi.yaml` carries
only `categoryCode`, no label, and `api/chat.ts` states the deliberate stance that a label
"invented in the browser would be a second description of the same rule". The correct fix
adds a label to the wire — a `packages/contracts` change, which is LAW/G7 and yours to
approve. Evidence `40`, `63`.

**D4 — Pipeline health is a near-constant, and one counter contradicts the board. (Medium)**
`lib/selectors.ts` hard-codes `duplicates: 0`, `unverified: 0`, `itemDelay: 0` on the live
projection **and feeds those zeros into `pipelineHealth`**. So the client panel read
"Duplicates flagged **0**" while the board flagged two, "Unverified spend £0.00" with five
unreviewed documents, and "Pipeline health **99%**" that cannot move. Only `processing: 0`
carries a comment explaining itself. A health score that is always ~99% teaches an
accountant to ignore it — the same family as last walk's structurally-guaranteed D43
warning. Evidence `48`.

**D5 — The product hides its own practice name and its own intake address. (Medium)**
`context/AppContext.tsx:1256` blanks `practiceName`, `docEmail` and `whatsappNumber` on the
live path. Deliberate (to avoid showing seed values), but two of the three have real known
values, so: Settings → Profile → **Practice name is empty** while the header shows
"Halewood & Finch Accountants"; the client panel says *"Email lands at **—**"*; the Users
tab says *"Accounts inbox — Forwards to **—**"* under a "DOCUMENT OWNER ON EMAIL INTAKE"
label. Evidence `48`, `82`, `84`.

**D6 — The chase page tells the client their link dies today. (Medium, client-facing)**
The token's own payload expires **2026-09-15** (7 days). The page renders *"This page closes
itself on 2026-09-08"* — today. The team-invite page gets this right ("Link works until 15
Sept"), so the two disagree. A client reading it may abandon a link that has a week to run.
Evidence `59`.

**D7 — A "DEMO SURFACE" panel on the live product, saying something false. (Medium)**
`ChasesLiveBoard.tsx` renders "Message outbox — the client's phone", tagged **Demo surface**,
reading *"With the demo sender nothing leaves this machine"* and *"Nothing sent yet"* —
beside a chase whose state is **SENT** and which really was delivered by SES. Staging runs
`EMAIL_SENDER=ses`, so the panel's premise is wrong and its wording contradicts the row next
to it. Evidence `78`.

**D8 — Statement balances nobody could read print as £0.00 → £0.00. (Medium)**
The no-balance statement stores `opening_balance_pence = NULL` and
`closing_balance_pence = NULL` (verified in the database) and the board prints **£0.00 →
£0.00** on the very row whose verdict is "Cannot be checked". Third occurrence of the
`fromPence(null)` shape, after total (#277) and date (D2). Evidence `50`.

**D9 — The coding card cites a rule that argues against its own answer. (Medium)**
The Currys invoice: suggestion **"Fixed assets: Plant and equipment"** (capital), reasoning
*"…£749.99 net which is below the £1,000 capitalisation threshold — but this is kitchen
plant and equipment capitalised as a fixed asset"*, and **RULE:
HARDWARE_PER_UNIT_BELOW_THRESHOLD** — a rule that maps to `REVENUE` in
`capital-revenue.ts`. The model is given the threshold, correctly found the amount below it,
then overrode the practice's own capitalisation policy while citing that policy as its
authority. `parseModelCodingSuggestion` already guards exactly this class for
`SUPPLIER_MEMORY` ("a model may not claim the client's own history as its authority") but
guards no other basis. Evidence `38`.

**D10 — The chase asked the client for receipts that cannot exist. (Medium, client-facing)**
The approved message read: *"we're missing the receipts for FRESH DIRECT CD 4211 on 14 Aug,
**PAYROLL AUG STAFF** on 21 Aug and **HMRC VAT** on 28 Aug"*. A payroll run and a VAT
payment have no supplier receipt to send. `chaseSuppressed` exists in the schema and the
matching module's own comment describes suppressing lines that "have no paperwork in
existence to find" — nothing populated it. The message also sends raw bank descriptors
("CD 4211") to a client. Evidence `55`.

**D11 — The reviewer is shown database ids. (Low)**
The chase review lists "Chasing transactions: `cmts8x617005wyy8vozab1uyh`, …" and the
publish review lists "Document `doc_ab2fae7141…`". The reviewer's job is to check what is
being sent; opaque ids tell them nothing. Evidence `55`.

**D12 — Approve is offered, enabled and primary-styled, to a user who can never use it. (Low)**
Tom's Approvals card presented a full Approve button; clicking it returned **403**. The
server is right and the message is honest, but `PublishBatchDialog` is explicitly
role-aware ("Your role does not release") — the Approvals card is not. Evidence `74`, `75`.

**Also noted:** the extraction provenance caption prints the provider slug — "AI suggested:
**bedrock**" (`api/document-detail.ts:201`); the "choose a client" refusal dialog offers two
buttons that both dismiss ("Cancel" and "Close"); the invitee's TOTP steps are captioned
"CREATE YOUR PRACTICE ACCOUNT" to someone joining one; a `PRACTICE_STANDARD` user's header
shows no practice name at all.

## 4. Launch blockers — yours, not engineering's

**L1 — Stripe is in LIVE mode on a personal account.** The checkout session minted during
this walk was `cs_live_…`, `livemode: true`, against `acct_1RQtbxGMdHp4NCWv` — the personal
account `docs/runbooks/stripe-billing.md` §0 says "is **not** where launch goes". Any client
completing checkout on the URL you are about to send **is really charged**, into a personal
account, with a VAT invoice bearing the wrong entity.

**L2 — `[PLACEHOLDER]` on the public page.** The landing footer reads "VAT registration
number: **[PLACEHOLDER]**". The code comments say you supply it before launch. It is not a
bug to fix in code — but it is on the page a client sees.

**L3 — Four legal documents are drafts.** Terms of Service (11 unresolved), Privacy Notice
(23), Data Processing Terms (23), Refunds (4). The app correctly refuses to pretend: each
renders behind *"This document is still a draft… Please do not rely on it yet."* They also
need a solicitor's review before publication.

**L4 — Email intake is not connected.** `doc@neoting.neovogent.com` accepts mail: SES
received the test message and wrote it to
`s3://nt-staging-receipts-252959251643/inbound/` (87,712 bytes). Nothing ingests it. The
only EventBridge rule touching that bucket routes to the **ClamAV scan queue**; there are no
Lambdas and no ingest queue subscription. `EMAIL_SOURCE` defaults to `fixture` and staging's
Terraform says so explicitly: *"EMAIL_SOURCE stays `fixture` — the s3 poller is a separate
process"*. The consumer exists in the repo (`email/inbound/email-intake-runner.ts`,
`s3-email-source.ts`) and is simply not deployed. **A client who forwards an invoice gets no
bounce and no document**, and mail accumulates unprocessed in S3. This pairs with D5: the UI
offers "Email" as a channel and shows the address as "—".
